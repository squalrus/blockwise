## API (`apps/api/src/app.ts`)

Auth gates:

- **public** — no auth, or `attachOptionalAuthUser` (personalizes response if a token is present, never blocks)
- **auth** — `requireAuthUser` (any signed-in account)
- **business** — `requireBusinessAccount` (signed in + `account_type = 'business'`)
- **venueOwner** — `requireVenueOwner` (approved claim on the venue at `:id`)
- **admin** — `requireAdmin` (admin of *at least one* neighborhood, no `:id` to scope by — list-style routes only)
- **neighborhoodAdmin** — `requireNeighborhoodAdmin` (admin of the *specific* neighborhood at `:id`)

## History

- **2026-09-02** — Monitoring's Errors sub-tab gains an App/API/Marketing source filter, and `apps/marketing` gains client error reporting for the first time. `error_log.source`'s check constraint widened from `('api', 'web')` to `('api', 'web', 'marketing')` (`20260902060000_error_log_marketing_source.sql`); `get_monitoring_analytics` gained a `p_source` param narrowing `errors_over_time`/`recent_errors` (v11, `20260902070000_monitoring_analytics_fn_v11.sql`), threaded through `GET /admin/monitoring/analytics`'s new `?source=` query param. `ErrorsBySourceStats.tsx` tiles are now clickable filters (mirroring the existing status-code-tiles pattern), labeled App/API/Marketing (source `web` reads as "App" in the UI — the value itself is unchanged, since apps/web is this dashboard's original "app" frontend). `POST /monitoring/client-errors` gained an optional `source` field (defaults to `"web"` for existing callers) so `apps/marketing` — previously fully static with zero error capture — could add its own `ClientErrorReporter.tsx`/`error.tsx`/`global-error.tsx`, mirroring apps/web's. Since marketing is a separate Netlify site with no co-located API function, its reporter goes through a new same-origin `/api/*` proxy (`apps/marketing/netlify.toml`'s redirect to `app.tryspored.com`, plus a matching local-dev rewrite in `next.config.ts`) rather than opening CORS on apps/api, consistent with apps/web's own "no cross-site CORS" precedent. Performance (request volume/latency) deliberately did *not* get the same App/Marketing split — that data is entirely `apps/api`'s own backend request timing today, and neither frontend's page-render time is instrumented, so a source filter there would have nothing real to filter. It gained a different filter instead: a route-scope pill row (App/Admin/Auth) narrowing every request_log-derived chart there to the public-facing app, an owner/admin dashboard (`/admin/*`, `/neighborhood-admin/*`, `/business/*`), or auth endpoints — this axis *is* real, since `request_log.path` already distinguishes them, no new instrumentation needed. New `monitoring_route_scope(path)` SQL helper (`20260902080000_monitoring_analytics_fn_v12.sql`) centralizes the path-prefix mapping; `get_monitoring_analytics` (v12) takes `p_route_scope`, threaded through `GET /admin/monitoring/analytics`'s new `?route_scope=`.
